# Architecture

This page describes how Radio Bot is put together as implemented in `src/`. It is written for contributors and for operators who want to know what the process does. The product requirements are in [the PRD](PRD.md). Where the two ever disagree, the code is authoritative.

## Process overview

Radio Bot is a single Node.js 24 process. The entry point is `src/index.ts`, which:

1. Loads and validates configuration (`src/config/env.ts`, Zod). If configuration is invalid it exits with code 78. It also refuses `TELEMETRY_ENABLED=true`.
2. Creates a Pino logger that redacts the Discord token, URL fields and auth headers (`src/observability/logger.ts`).
3. Builds the application with `createApp()` (`src/app.ts`) and starts it.
4. On `SIGTERM` or `SIGINT`, tears everything down and force-exits after 10 s. On `SIGHUP`, reads the installed-packs folder again (`app.reloadPacks()`), which `radio-bot packs` and `systemctl reload radio-bot` send after changing it.

There are no other services. State lives in one SQLite file, plus the installed station packs in a folder next to it. All network traffic is outbound: the Discord gateway and voice servers, the station stream hosts, each pack's official station list page (sync), the official pack library on `github.com` (its `index.json` and pack bundles), and Discord's CDN (for `/radio import` attachments). The only listening socket is the optional diagnostics endpoint, which binds to `127.0.0.1`.

## Wiring (`src/app.ts`)

`createApp(config, logger)` constructs everything in this order:

1. **Database.** `new Db(DATABASE_PATH)` opens SQLite with WAL, foreign keys, `busy_timeout`, a page cache of at most 8 MB (`cache_size = -8192`) and temporary tables in memory (`temp_store = MEMORY`), then runs `db.migrate()`. If the database already has a schema and migrations are pending, a backup is written to the `backups/` folder next to the database first. `Db` keeps each prepared statement and reuses it, since compiling one costs more than running a small query (the cache holds up to 500 statements and is emptied when full). It counts rollbacks, and `onRollback()` tells a repository when a transaction or savepoint it wrote in is rolled back. `StationRepository`, the only writer of the station tables, caches stations and sources separately, parsed and frozen, and keeps both current in place, because reading a big catalogue again takes tens of milliseconds for each table on the thread that sends voice packets:
   - a write to a source (every check and playback result, a new source, a move to another station or priority, a delete) re-reads only that row and puts it in its station's list;
   - a write to a pack station (a new one while a pack is installed or synced, a rename, a new order, a status change) re-reads only that row and puts it where the full read would (`ORDER BY` pack, order, name with SQLite's `NOCASE` collation, which `compareNoCase()` matches, then ID); a catalogue sync marking the stations still on its list as seen re-reads only those rows, in one query per batch;
   - adding, editing or removing a server's custom station re-reads only that server's custom stations, and removing one drops its sources from the cache;
   - a write made while a table wasn't cached, or the rollback of a transaction that wrote that table (or read it into the cache), leaves the next read to read the whole table again. A rollback that touched neither table, such as a failed settings write, keeps both caches.

   `changeCount` goes up on every station or source write, so views can keep what they work out from the catalogue until it changes.

   Each server's custom stations are kept in their own list. So on the thread that sends voice packets, suggestions, browse pages, coverage counts and availability badges are map lookups rather than queries. A single-row read (`getStation`, `getSource`) uses the cache only while it is current; otherwise it queries that row.
2. **Repositories.** `StationRepository`, `GuildRepository` (seeded with the installation defaults for quality mode, idle mode and resume) and `MetaRepository` (a key/value store for things like the component-signing secret and command hashes).
3. **Station packs.** `PackRegistry.load()` loads and validates every pack folder in `catalog/packs/` (which holds only the ignored `_template/` now), in `EXTRA_PACKS_DIR` and in the installed-packs folder next to the database (`installedPacksDir()`). A mistake in a `catalog/packs/` or `EXTRA_PACKS_DIR` pack stops start-up; an installed pack that fails its checks or clashes with another is skipped, logged and kept in `PackRegistry.skipped`, so one bad download never takes the radio off the air. It applies `ENABLED_PACKS` and `DISABLED_PACKS` on top of each pack's `enabledByDefault`. `seedPacks()` then runs in a single transaction and upserts each pack's `stations.json` and `sources.json`. Nothing is playing yet, so this one transaction is safe here; packs added later are written in slices (see `pack-manager.ts` below). Seeding:
   - keeps runtime evidence and guild data;
   - applies `enabled`/`disabledReason` from the manifest;
   - disables (never deletes) any pack source that has been removed from its manifest.

   Then two one-off costs are paid before anything plays, not by the first listener: `warmLocaleData()` sets up ICU's collation and display names (about 30 ms the first time; text comparison goes through one shared collator, `compareText()`), and `prepareStations()` works out every station's normalised names for search.
4. **Network policy.** It creates a `UrlPolicy` (honouring `ALLOW_INSECURE_HTTP_STREAMS`) and a `SafeHttpClient` that enforces it.
5. **`ProcessRegistry`.** Every FFmpeg and FFprobe child process is registered here.
6. **`SourceService`.** This is the source-validation boundary, with the probe concurrency limit and the operator disable lists.
7. **The discord.js `Client`.** Its intents are **`Guilds` and `GuildVoiceStates` only**. Message, presence and reaction caches are disabled, member and user caches are capped at 200 entries, and `allowedMentions` is empty.
8. **`Notifier`, `SessionManager`, `CatalogueSync`, `PackManager`, `CustomStationService`**, and `ComponentIds`, whose HMAC secret is generated once and persisted in `app_meta` so that panel buttons keep working across restarts.
9. **`RadioController`**, which receives every interaction, then **`PresenceUpdater`** (the bot's status) and **`VoiceStatusUpdater`** (each server's voice channel status). The session manager gets the station-visibility filter used at boot and the leave hook that clears a channel's status.

`start()` then does the following:

- Writes a heartbeat at once, replacing any left by a previous run, so health checks wait for this process.
- Starts the database's checkpoint worker (`WalCheckpointer`, see [`persistence/`](#persistence)). From then on the bot's own connection never checkpoints.
- Runs `ffmpeg -version`, `ffprobe -version` and `ffmpeg -encoders`. It logs an error if a binary is missing or `libopus` is absent.
- Checks both voice transport encryption modes (`checkVoiceEncryption()` in `voice/encryption.ts`): OpenSSL's AES-256-GCM, and one XChaCha20-Poly1305 round trip through `@noble/ciphers`, the package `@discordjs/voice` loads for the mode every Discord client must support. It logs `voice encryption available`, or an error if XChaCha20-Poly1305 is missing.
- With `VOICE_THREAD=worker`, starts the voice worker and runs its self-test (see [`voice/`](#voice-sessions-and-the-playback-state-machine)), falling back to the main thread if it fails.
- Puts back missing packs (`PackManager.restoreMissing()`): packs the database has stations from that aren't loaded, and that nobody removed on purpose, are installed from the official library, so favourites, queues and resumes keep working after an update stopped shipping a pack or a backup was restored on a new machine. This happens before the bot logs in, so nothing is playing yet; start-up waits for it (each download is limited to 20 s), and if the library can't be reached it logs a warning and the daily check tries again.
- Subscribes to interactions, client errors, shard disconnects (recorded as incidents) and `GuildCreate` (registers commands for a newly joined server, always, since a server that removed and re-invited the bot has lost them).
- On `ClientReady`, fetches the application (needed for the owner check), registers guild commands, writes a heartbeat (in the background: the restore doesn't wait for the disk), runs `restoreOnBoot()`, sets the bot's status and re-renders each server's control panel, one at a time (`guildsWithPanel()`). On every `ShardReady` it sends the status again, because a new gateway session starts without it.
- Starts the event-loop monitor and these timers:
  - a heartbeat every 30 s. It is written asynchronously (`HeartbeatWriter`), so a slow disk never holds up voice packets: the snapshot goes to `health.json.tmp`, which is then renamed over `health.json`, so a reader always sees a whole file. Writes never overlap: one asked for while another is under way waits, and if several wait, only the newest is written;
  - every 20 s, the bot's status (`PresenceUpdater`) and each server's voice channel status (`VoiceStatusUpdater`), each sending only changes;
  - every hour, rate-limit sweeping and the clean-up of old check results (`pruneProbeHistory()`). The clean-up is automatic background work (see `source-service.ts`), so it runs one at a time with source checks and waits while a stream starts or settles in. It deletes results older than `PROBE_HISTORY_DAYS` 250 at a time through the `started_at` index, giving the event loop a turn between batches: one `DELETE` of thousands of rows a month after a big check could hold up voice packets for tens of milliseconds. The per-source limit is applied as each check is written; trimming every source to it again only happens when `PROBE_HISTORY_LIMIT` is lower than the limit last applied (kept in `app_meta` as `probe_history.trimmed_to`), 50 sources at a time. A clean-up still running an hour later isn't started twice;
  - every 5 min, a refresh of the control panel of each server that has a session, one server at a time, yielding to the event loop in between;
  - the catalogue sync. Each enabled pack that declares an official list gets its own schedule (`scheduleCatalogueSyncs()` in `sync-schedule.ts`). It first runs when it is due, or about 10 min after start if it has never run, and never sooner than 1 min; then every `CATALOG_SYNC_INTERVAL_HOURS`, with up to 15 min of jitter on each run. Each pack has one pending timer, and nothing is scheduled once shutdown begins. Node can't wait longer than about 24.8 days with one timer, so a longer wait is made of several timers in a row. A scheduled sync is automatic background work: when its timer fires it joins the queue that background source checks use (`SourceService.runInBackground()`), so it runs one at a time with them and waits while any stream is starting or settling in (its first 3 minutes). A sync an admin starts with `/radio packs sync` runs at once, since someone is waiting for it. Shutdown cancels a scheduled sync that is still running. Installing or removing a pack re-plans the schedules, since it changes which packs have an official list;
  - the daily pack check (`PackManager.check()`), first 15 to 30 min after start, then about every 24 h (with up to an hour of jitter). It runs as automatic background work. It notes newer versions of installed packs (the bot's operator installs them; nothing updates by itself), removes packs installed from the official library that the library has withdrawn (with a notice for `/radio packs installed`, stopping any session playing one of their stations), and retries putting back missing packs.
- Starts the optional diagnostics HTTP server on `127.0.0.1:DIAGNOSTICS_PORT`. If the port is in use, it logs a warning and the bot runs without it.
- Logs in.

`stop()` clears the timers and the sync schedule, clears every voice channel status (waiting at most 2 s), stops the event-loop monitor, closes the diagnostics server, destroys every session, stops the voice worker if there is one (its leave messages still go out through the gateway; at most 2 s), closes the notifier, destroys the client, writes a last heartbeat (and waits for it), kills any remaining child processes, stops the checkpoint worker, runs a final checkpoint that empties the write-ahead log into the database file, and closes the database.

## Modules

### `streams/`: finding, fetching and judging sources

- **`url-policy.ts`** does syntactic URL validation before any network activity. It allows only `http:`/`https:` (and `http:` only when `ALLOW_INSECURE_HTTP_STREAMS=true`). It rejects:
  - URLs over 2048 characters;
  - user info (credentials) in the URL;
  - ports below 1024 other than 80 and 443, and a deny-list of common internal-service ports;
  - `localhost`, `metadata`, `.local`, `.internal`, `.lan`, `.home.arpa`, `.arpa` and similar suffixes, plus single-label host names;
  - literal private or reserved IPv4 and IPv6 addresses.

  The IPv6 check understands IPv4-mapped, IPv4-compatible, NAT64 and 6to4 forms, and anything outside `2000::/3` is blocked. `assertAddressAllowed()` checks a resolved address.
- **`safe-fetch.ts`** (`SafeHttpClient`) is the only HTTP client used for stream URLs, playlists, manifests, HLS segments, the official station list, the pack library and import attachments. On every hop it validates the URL, resolves DNS itself and rejects the hop if *any* resolved address is blocked. It pins the socket to the validated address (no second lookup, so DNS rebinding cannot swap the target), re-checks the connected peer address, follows at most 5 redirects manually and re-validates each one. It caps header size (16 KiB), per-hop header time and body size, and sends a User-Agent of FFmpeg's network library: `Lavf/<version>`. At start-up, `app.ts` sets the exact version from the installed FFmpeg (`lavfUserAgent()` parses `ffmpeg -version`). The fallback is `Lavf/61.7.100`, and `STREAM_USER_AGENT` overrides it. FFmpeg is what decodes the audio, so this is accurate. Some stream hosts, including the host of the first pack in the library, refuse unknown clients but serve standard media players. The client never imitates a web browser and sends no `Referer`.
- **`playlists.ts`** contains parsers for PLS, plain M3U and HLS (master and media). For HLS it ranks audio renditions. `BANDWIDTH` values that are really sample rates (such as 44100, which at least one pack's stream host declares) or that are implausibly low are ignored (`plausibleBandwidth()`). The order is: audio-only variants by declared bandwidth, then variants without `CODECS`, then alternate audio renditions (groups used by higher-bandwidth variants first, since they normally carry the better audio, then the default), then muxed audio and video variants (whose `BANDWIDTH` says nothing about audio). It caps playlists at 5000 lines and strips ID3 from packed-audio segments.
- **`input.ts`** opens a source as a byte stream:
  - `openSourceInput()` follows PLS/M3U indirection up to 2 levels deep and tries the first 5 entries. It rejects HTML, JSON and image content types.
  - For direct streams it requests ICY metadata and runs an `IcyDemuxer`, which strips the interleaved metadata blocks and surfaces `StreamTitle` as now-playing text. The text is read as UTF-8 when valid, otherwise as Windows-1252 (older SHOUTcast servers send Latin-1). `parseIcyStreamTitle()` trims separators left by an empty half ("Artist - "), and treats an empty, symbol-only or placeholder title ("Unknown", "Advert" and similar) as cleared, so the previous title is not left showing. The text may be a song, a show or anything else the station chooses, so it is labelled **On air**, never parsed into artist and title. HLS sources carry no title: ID3 tags in segments are skipped, not read.
  - For HLS it uses an `HlsReader`. The reader starts 3 segments behind the live edge and polls the playlist at half the target duration. Each poll resolves the addresses of new segments only (`parseHls(…, { minSequence })`), so a long DVR-window playlist costs little to read again, and every segment keeps its RFC 8216 sequence number even when its address is unusable. It retries each segment (and each fMP4 init section) once, skips a segment that still fails, and gives up after more than 3 consecutive segment failures (`HLS_SEGMENT_FAILED`) or 5 consecutive playlist failures (`HLS_PLAYLIST_FAILED`). It refuses encrypted playlists (`HLS_ENCRYPTED`) and resynchronises near the live edge if it falls out of the window, or if the media sequence numbers go backwards further than the playlist is long (for example after an upstream encoder restart). A playlist that is only a little behind what was already sent (a stale copy from another CDN node) is ignored until the next poll, so no audio is sent twice. Segments are capped at 16 MiB and playlists at 512 KiB.
- **`probe.ts`** (`probeSource()`) runs one bounded technical probe. The defaults are a 22 s total budget, up to 15 s for the server's first response (playback keeps 10 s; the longer wait lets a slow server that ends with 404 be reported as `NOT_FOUND`, not a timeout), 7 s of sampling and at most 2 MiB held in memory. It runs `ffprobe` (format, stream and packet data) and then an FFmpeg decode check over the same in-memory sample, which stops at the start of the sample's last packet (from FFprobe's packet positions) so that the probe's own mid-frame cut is not counted as a decode error. The sample is discarded afterwards. Measured bitrate is payload bits divided by audio duration from the packet table, needing at least 3 s of packets; it is not network timing. The probe records which bitrate evidence it used: `measured`, `codec-metadata`, `manifest`, `advertised` or `unknown`. A direct stream that ends inside the sample window fails with `STREAM_EOF` (live radio doesn't end; a short "offline" file does), and a run-out budget is `PROBE_TIMEOUT`, never `CANCELLED`. An unreadable `icy-metaint` header makes the input re-request the stream without ICY metadata, so metadata bytes can never reach FFmpeg.
- **`identity.ts`** decides whether a source plays the station it claims to. It uses provenance, the ICY stream name (a pack's brand labels, such as a network name shared by several stations, are ignored) and optional time-aligned audio correlation. For a comparison (`compareSources()`), FFmpeg decodes both samples in child processes at the lowest priority; the cross-correlation of the two envelopes then runs on the main thread in slices of 64 lags that give the event loop back in between (`correlateEnvelopesInSlices()`). Each window's energy comes from prefix sums, so only the products are added up for each lag. See [station-verification.md](station-verification.md).
- **`ranking.ts`** contains the eligibility gate and the correctness-gated, multi-criteria selection (`selectSource()`): the transport tier comes first (direct, then unknown, then HLS as a last resort), then evidence. It returns a selected source, a distinct fallback, a conclusion and a human-readable explanation.
- **`source-service.ts`** (`SourceService`) is the boundary. It is the only component that probes. It deduplicates in-flight probes: several callers can wait on the same probe, and if one of them cancels, only that caller stops waiting. The shared probe is neither cancelled nor recorded as a failure. It limits concurrency globally (`MAX_CONCURRENT_PROBES`) and per host (one at a time). It applies probe outcomes and identity decisions to the database, records probe history, applies the operator disable lists, and works out station availability and coverage counts. Playback calls `prepareForPlayback()`, which uses cached evidence when an eligible source exists and probes in the foreground, best candidate first, only when nothing is eligible. It starts no background work of its own: the session's first check for a better source after the settle period (below) calls `refreshStation()`, and background checks run one at a time through their own queue. A failing source's next automatic check backs off (`nextAutomaticCheck()`: about 10 min, 1 h, 6 h, 12 h, then once a day; a gone address, `NOT_FOUND`, starts at 12 h); a success resets it, and `/radio rescan` ignores it and reports progress after each source. For a play with no working source, `needsProbe(…, 'foreground')` re-checks failing sources at most every 10 min (hourly after a day without success). `isPaused()` (no success for 7 days and 5+ failures in a row) makes a source never due, in either mode, until an admin rescan succeeds, the operator runs **Check all sources again**, or a pack update gives it a new address. A foreground `probe()` interrupts a background check of another source on the same host (its result is discarded, not recorded); a play that joins a background check of the same source makes it uninterruptible. Playback reports health back through `recordPlaybackSuccess()` and `recordPlaybackFailure()`, and the latter trips the circuit breaker. Background work runs one job at a time through `runInBackground()`. All of it waits while any stream is in its first 30 s (`holdBackground()`, called by the session at each start). *Automatic* work, which nobody is waiting for (background checks, the operator's full check, scheduled syncs, the daily pack check and the hourly clean-up), also waits until the newest stream has played for 3 minutes after its first audio (`settleBackground()`, `SessionTimings.backgroundSettleMs`), because Discord's client is still settling its own buffer then and a late packet is most audible; if a stream starts while automatic work waits for its turn, the automatic work lets other work go first. Work a user asked for (installing, updating or removing a pack) only waits for the 30 s hold. A stream starting also stops any background check nobody else is waiting for; it records nothing and is queued again later. Background checks (`refreshInBackground`) queue each source once and decide whether it is still due when its turn comes. Stopping the operator's full check only stops a check nobody else waits for: a play that joined it still gets its result. `coverageByProvider()` keeps each pack's coverage counts for at most 60 s, or until `changeCount` or the disable lists change, and the eligibility walk behind coverage and availability (`isEligibleNow()` in `ranking.ts`) builds no reason strings and copies no rows. Each check's results are written in one transaction, and the source's history is trimmed to `PROBE_HISTORY_LIMIT` there; after its first run, the hourly job only deletes results older than `PROBE_HISTORY_DAYS`.
- **`full-check.ts`** (`FullSourceCheck`) is the bot owner's **Check all sources again** on `/radio packs installed`: every enabled source of every switched-on pack, ignoring back-off, cooldown and pause (custom stations, sources a pack ships switched off, the operator's disable lists, rights-blocked sources and sources playing somewhere are left out). It lists the sources in slices of about 2 ms, then hands them to `SourceService.checkInBackground()` one by one, so every check joins the same one-at-a-time background queue as `refreshInBackground`, waits while a stream starts, runs at the lowest priority and gives way to a play's check on the same host (each source is tried up to 3 times in all; a check stopped because a stream started is queued again and doesn't count). Only one run at a time; `stop()` (the Stop button, and shutdown) aborts the check in progress, which records nothing. Its state (running N of M, or the last run's summary) is kept in memory for `/radio packs installed`.

### `audio/`: one FFmpeg process per playing server

- **`ffmpeg.ts`** holds the `ProcessRegistry`, which tracks every child process by owner (`session:<guild>`, `probe:<source>`, `identity:<source>`) and kind, can kill by owner or kill everything, and counts processes spawned and reaped. `terminate()` sends SIGTERM, then SIGKILL after 2 s. `runWithInput()` runs a short-lived tool over an in-memory buffer on stdin with a timeout, a stdout cap and abort support. Those jobs (stream checks, comparisons, version checks) run at the lowest CPU priority (`lowerPriority()`); only the live encoder keeps normal priority, so on a busy or single-core host the stream is served first. On Linux, `lowerPriority()` also sets the child's `oom_score_adj` to 1000, asynchronously and best effort, so the kernel kills stream checks before the bot or its encoder. The deployments rank the bot above other workloads: `cpu_shares` and `oom_score_adj` in `compose.yaml`, and `CPUWeight`, `IOWeight` and `OOMScoreAdjust` in the systemd unit. None of them sets a quota or limit. `checkFfmpeg()` checks the versions and that `libopus` is present.
- **`encoder.ts`** contains `planEncoder()`, which chooses the Opus target from the quality mode, the source's own bitrate (`sourceBitrate()`: measured, then codec metadata, then manifest or advertised; the target is rounded up, and raised to the re-encode floor of 128 kbps, or 96 for mono, in `maximum`) and `MAX_OPUS_BITRATE_KBPS` (it reports the channel's bitrate setting but doesn't use it as a cap), and `buildEncodeArgs()`, which builds the fixed FFmpeg argument list. See [audio-quality.md](audio-quality.md).
- **`pipeline.ts`** (`AudioPipeline`) spawns the encoder. It pipes the policy-checked source bytes into stdin and passes stdout through a counting `Transform`, which feeds the stall watchdog and the observed output rate. It emits `failed` exactly once: `FFMPEG_SPAWN`, `FFMPEG_EXIT` with the last stderr lines (redacted), `STREAM_EOF`, or an input error. `stop()` is idempotent. It closes the network input and the pipes and reaps FFmpeg.

### `voice/`: sessions and the playback state machine

- **`voice-thread.ts`** (`VoiceThread`, `VOICE_THREAD=worker`) runs every voice connection on one long-lived worker thread (`worker/voice-worker.ts`, logic in `worker/host.ts`), with its own event loop, heap and garbage collector, so nothing the main thread does (commands, synchronous SQLite, gateway messages, its own garbage collection) can hold up the 20 ms packet timer. The worker owns each `VoiceConnection`, `AudioPlayer` and live queue (Ogg demux only, no decoding), and the UDP, WebSocket and DAVE traffic. FFmpeg, the station input, `SafeHttpClient`, `ProcessRegistry` and the session state machine stay on the main thread. What crosses over:
  - the encoder's Ogg pages, about fifty a second per stream (one 20 ms packet each), moved without copying where possible. The worker writes them into a 256 KB buffer and asks the main thread to pause the encoder's output while it is full, so back-pressure still reaches FFmpeg;
  - the gateway: the worker gives `@discordjs/voice` a relay adapter, and the main thread opens the real one with `guild.voiceAdapterCreator`. Join and leave payloads go out through the main thread's Discord connection, and voice state and server updates come back;
  - a snapshot of each link (status, channel, playback time, stats), pushed every second and on every state change, so the session's synchronous getters keep working;
  - the link's events (lost, audio ended, reconnected, connection error, interrupted, restored), as they happen;
  - Discord's receiver report, only while `/radio stats` is open: the main thread arms and disarms the worker's reader (`reports`) and asks for a reading when it draws the panel (`readReport`, answered by `report` with the same request ID, or given up after 1 s). The report and the key stay in the worker; only the figures come back;
  - the worker's own event-loop delay and garbage collection, every 5 s, for `/radio stats` and the log (a delay of 50 ms or more in the worker is a warning).

  Every message carries a link ID, and audio a stream ID, so anything still in flight for a detached link or an older stream is dropped. If the worker stops, every link reports itself lost (the session reconnects, as after any lost connection) and the worker is started again after about 1, 5, 15 and then 30 s. At start-up the worker must load the voice libraries and create a DAVE session (`selfTest()`); if it can't, the bot logs an error and runs voice on the main thread. The worker's heap is capped at 96 MB and it keeps normal CPU priority. It never writes to the console: its log lines go through the main thread's logger.
- **`link.ts`** (`DiscordVoiceLink`) joins the voice channel through `@discordjs/voice` with `selfDeaf: true`, `selfMute: false` and `daveEncryption: true`. `play()` reads the encoder's Ogg Opus through a live queue (`liveQueueFrom()`, below), told how much audio arrives in one go (`chunkMs`: an HLS segment's length, or nothing for a continuous stream), and creates an `AudioResource` from the queue's Opus packets with `inputType: StreamType.Opus` and no inline volume. The queue's catch-ups are passed on as `caughtUp` events, and its figures are part of `stats()` (`live`). On disconnect it tries to reconnect up to 5 times. Close code 4014 that does not reconnect within 5 s is treated as a kick. A connection can also stop being ready without ever reaching Disconnected: when the voice WebSocket of a resume closes too, the library re-sends the gateway's voice join, moves to `signalling` and waits for Discord's answer (a voice server) with no timeout of its own, so if the answer never comes it stays silent indefinitely. So each interruption starts one timer (`VOICE_STUCK_MS`, 30 s, cleared when the connection is ready again, detached or destroyed). If the connection still isn't ready when it fires and no reconnect is already under way (the reconnect loop above outlasts 30 s and is left to finish), the link rejoins once on the same connection (`rejoin()`, then 15 s for Ready); if that doesn't bring it back, it gives the connection up as `reconnect_failed`, and the session's handling of a lost link joins again from scratch, which asks Discord for a new voice session and so a new voice server, with the session's own backoff and notice. The timer looks again every 30 s while the connection isn't ready. 30 s is longer than the library's own resume (a second or two), a reconnect after a disconnect (2 s plus 15 s for Ready) and a first join (20 s), so the link never cuts across a recovery that is getting somewhere. Each step is emitted as `recovering` (`step`: `rejoin` or `fresh`, the connection's status, and `afterMs`), which the session logs as a warning (`voice connection stuck; rejoining`, `voice connection still stuck; joining again from scratch`) and counts as `voice.stuck`; with `VOICE_THREAD=worker` the voice worker passes it on like the link's other events. It costs one timer per interruption, nothing per packet. The player uses `NoSubscriberBehavior.Play`. While the connection isn't ready, for example while the library resumes a closed voice WebSocket (close codes below 4000 and 4015, or a UDP keep-alive timeout), the library sends nothing, and the player reads frames on and drops them. The link leaves it that way on purpose: playback stays at the live edge, and the gap is heard once rather than paid for with lasting delay (see "Live means live" in [AGENTS.md](../AGENTS.md#live-means-live)). Audio isn't sent during a resume either: Discord's documentation doesn't say that is allowed, and the DAVE group may have changed by then. When the connection is ready again, the link tells the live queue to catch up (`catchUp('resume')`), so a backlog past the cushion goes where the gap just heard hides it. The link emits `interrupted` (the new status, whether the library is resuming, and the WebSocket close code from a listener that runs before the library's) and `restored` (`afterMs`, how long the connection was away; `skippedMs`, how much the player read on and dropped, counted from the player's own state changes, so a Stop or a new station meanwhile is counted as it happened; and `caughtUpMs`, what the live queue dropped then). A close from a socket the library has already replaced is ignored. The session logs both at info level. Nothing is added per packet. `encryption()` reports whether DAVE was negotiated, using the voice privacy code. `timePackets()` wraps the connection's `dispatchAudio` once, so the link's `PacketTiming` (`packet-timing.ts`) counts packets sent more than 40 ms after the one before while playing, and the longest gap, and keeps the time and gap of the last 16 late ones; a pause or a voice reconnect resets the gap. `stats()` reports them for `/radio stats`, with `silenceMs`: the silence the player sent because no audio was ready (the player's playback time less the resource's). The session samples both every 5 s; it clears its packet-rate samples on a voice reconnect, which starts the connection's packet count again.
- **`receiver-report.ts`** reads the RTCP Receiver Reports Discord's voice server sends the bot about once a second, which `@discordjs/voice` ignores, on demand only (see [audio-quality.md → Discord's receiver report](audio-quality.md#discords-receiver-report)). `ReportWatch`, one per session, arms the link when an admin opens or refreshes `/radio stats` and disarms it after the last Close, 15 minutes after the last open (an `unref()`'d timer), or at once from `stop()` (stop, leave, a lost or torn-down link, an interruption, a reconnect, shutdown). Armed, the link (`armReports()`) puts a `ReceiverReportTap` on the voice UDP socket: one listener that copies each report into one fixed 256-byte slot. The link disarms itself when the connection stops being ready, the channel changes, or it is detached or destroyed, and a reading taken on a different socket than the one armed disarms it too. `receiverReport()` decrypts the slot with the connection's key (`openReceiverReport()`: AES-256-GCM through node:crypto, XChaCha20-Poly1305 through `@noble/ciphers`), parses the report block, and counts the packets Discord expected from sequence numbers. Disarmed, nothing is attached.
- **`live-queue.ts`** (`LiveQueue`, `liveQueueFrom()`) is the live edge of a stream: the one queue of Opus packets between the encoder and the 20 ms sender, so the bot knows how far behind live it plays and keeps that small (see [audio-quality.md](audio-quality.md#staying-live)). `liveQueueFrom()` demuxes the Ogg stream eagerly, with no back-pressure, so any backlog builds up in the queue, where it is measured, not in the pipes before it. The cushion is the chunk plus a margin. The chunk (`chunkMs`) is how much audio arrives in one go: 0 for a continuous (ICY) stream, the playlist's target duration for HLS, clamped at `LIVE_CHUNK_MAX_MS` (12 s). The margin starts at `LIVE_CUSHION_MS` (1 s). Before the first packet goes out, the queue waits until the station's connect burst has landed (audio no longer arriving faster than real time for 0.2 s, or 1 s for HLS, whose first segments come with a fetch between them) and at least the 0.3 s settle period, then drops the burst down to its cushion; a second look shortly after (`settle`: 1 s later for a direct stream, the chunk plus 1 s for HLS) is a backstop for any late part of it. A network gap (the queue empty for two frames, 40 ms, or more) adds `LIVE_CUSHION_STEP_MS` (0.5 s) to the margin, up to `LIVE_CUSHION_MAX_MS` (3 s), so the cushion is at most 12 s + 3 s = 15 s; 30 minutes without a gap takes a step off again, applied at the next catch-up (for example the next voice resume). After a gap the queue hands the player nothing until the margin is back in hand (the refill: for HLS, as soon as the next segment arrives), and the floor and drift are left alone meanwhile. A backlog past the cushion is dropped when the refill is done and again shortly after, on `catchUp('resume')` from the link, or on its own once the queue's floor is `LIVE_LIMIT_MS` (3 s) above the margin; less than 0.2 s is left alone, and the queue never holds more than `LIVE_CAP_MS` (30 s). Every catch-up is reported through `onCatchUp` (`reason`: `start`, `settle`, `gap`, `resume`, `limit` or `cap`; `droppedMs`; `cushionMs`). The queue's lowest level over the last few seconds (its floor), followed over 10 minutes, gives the station's clock drift in ppm; it is reported, never corrected, because correcting it would mean resampling. Per packet the work is constant (an array push or an index step, a clock read and a comparison); the floor, the drift, the cushion's easing and timed catch-ups run on a once-a-second timer. `stats()` gives the depth, floor, cushion, audio dropped at the start and since, the number of catch-ups and gaps, and the drift.
- **`state-machine.ts`** defines the PRD §9.1 states: `IDLE`, `JOINING`, `CONNECTED`, `BUFFERING`, `PLAYING`, `SWITCHING`, `RECOVERING`, `FAILING_OVER`, `STOPPING`, `LEAVING` and `ERROR`, with the allowed transitions. An unexpected transition is logged, not thrown.
- **`session.ts`** (`GuildSession`) handles one server. It owns at most one voice link and one pipeline. It keeps the **desired state** (persisted in `guild_playback_state`: `idle`, `playing`, `paused_empty`, `stopped`, `left` or `kicked`) separate from the runtime state. A generation counter means a newer command always supersedes an older one that is still pending. Overlapping play requests share a single voice connection attempt, so a quick double-click doesn't open two connections. A `/radio stop` that arrives while the bot is still joining is honoured: nothing plays once the join completes. `/radio join` to a different channel while a station is playing moves the bot and brings the station along. `useSource()` plays the current station from a source a listener chose (`manualSourceId`); later restarts of the same station use it, and it is dropped when the station changes or that source fails over. The session also contains:
  - the stall watchdog, which also restarts when a play takes over a connection that a leave was still holding open;
  - the live-lag check, a last resort behind the live queue: playback more than 45 s behind live reopens the same source. The lag is the time since the encoder's first output less the audio played, without what has already been made up: the audio the live queue dropped to catch up (not the connect burst dropped at the start, which goes before the first packet plays) and the gaps the HLS reader left when it skipped forward to the live edge;
  - what the live queue is told about each stream (`playOptionsFor()`: for HLS, the playlist's target duration as the chunk that arrives in one go; nothing for a direct stream), an info-level log line for each of its catch-ups (`started behind live by the cushion; dropped the connect burst` at the start, `caught up with live` after that, `settle` included; a resume's is in the `voice connection ready again` line) and the `playback.caught_up` metric;
  - the retry, failover and circuit-breaker logic. Faults in the bot's own domain (FFmpeg failing to start, an internal error) are never counted against a source and are retried on the same source. If FFmpeg can't start and the retries run out, the session reports an error and tries again after 2 min, with no failover; after an internal error it fails over once the retries run out;
  - the "no eligible source" retry (after 15, 30 and 60 s, then every 2 min);
  - moving back to a better source: once a minute a steady stream checks whether its station's best source has worked again since it failed, and moves back to it when that is a real step up, at most once every 10 min and never over a listener's choice. A move back that fails before it has played steadily goes straight back to the source that was working, and the wait before trying that source again doubles each time (up to 4 h). It also re-encodes when a newer check measures the playing source more than 5 % higher;
  - planning the encoder from the stream actually opened: for HLS, a clearly higher rendition than the check measured sets the target (`withOpenedBitrate()`);
  - the idle modes;
  - re-encoding when the target changes after the quality mode or the manual bitrate is changed on the `/radio config` settings card, or the settings are reset there (`refreshEncoder()`);
  - info-level log lines for every stop and every leave, with the reason (`command` for a listener's Stop or Leave; `station_removed` and `pack_removed` for stops; `channel_empty`, `idle_after_stop`, `channel_deleted` and `moved_disallowed` for leaves), and for the link's interruptions and recoveries.

  Timings are listed in [audio-quality.md](audio-quality.md#recovery-and-continuity).
- **`session-manager.ts`** (`SessionManager`) keeps one session per guild and enforces `MAX_ACTIVE_GUILD_STREAMS`. It wires gateway events:
  - moves: leaves if moved into a channel that isn't approved, or away from the preferred channel while *Channel lock* is on;
  - listener-count changes;
  - channel bitrate changes;
  - channel deletion;
  - guild removal. When Discord reports a real removal (`guild.available` is true), the session is destroyed and the server's data is purged with `GuildRepository.purgeGuild()` and `StationRepository.deleteGuildCustomStations()`, in one transaction. A server that is only unavailable because of an outage keeps its data.

  It also implements the boot policy (`restoreOnBoot()` / `bootDecision()`) and shutdown.

### `discord/`: interactions and authorisation

- **`commands/definitions.ts`** defines one `/radio` command with guild context and guild-install integration only. It uses exactly **25 top-level options**, which is Discord's maximum: 22 subcommands plus the `queue`, `source` and `packs` groups. **A new command must therefore go into a subcommand group, or replace an existing one.** **`register.ts`** registers it per guild with a REST `PUT` and skips the call when a hash of the definition is unchanged for that guild, unless registration is forced (as it is for a newly joined server).
- **`controller.ts`** (`RadioController`) handles every autocomplete, slash command, button, select menu and form (modal; so far only Browse's search box). A form's custom ID is signed and checked like a button's. Each handler builds an `AuthContext` from the interaction itself (roles from the interaction member, voice channel from the voice-state cache, so no member intent is needed). It calls `authorize()` and only then acts. Long operations defer their reply. `RadioController.handle()` logs every interaction at debug level with `describeInteraction()`, the time taken and the process's CPU time meanwhile.
- **`permissions/authorize.ts`** contains the capability matrix: `read`, `control` and `admin`. See [permissions.md](permissions.md).
- **`components/custom-id.ts`** (`ComponentIds`) produces signed, guild-bound component IDs with optional expiry. An ID is `rb2:<action>:<arg>:<expiry>:<signature>`:
  - the action is one of `COMPONENT_ACTIONS`, at most 7 characters (`MAX_ACTION_LENGTH`), and a new action must be added to that list;
  - the argument is at most 65 characters (`MAX_ARG_LENGTH`, the longest possible station ID), with a station ID's colon carried as a dot;
  - the expiry is counted in whole minutes from 1 January 2026, written in base 36 (five digits until 2140), and `0` means the ID never expires (control panels);
  - the signature is the first 16 characters of an HMAC-SHA256 over the guild ID and the rest of the ID.

  So every ID fits Discord's 100-character limit, whatever the station, and `make()` throws rather than build a longer one. `parse()` returns null for a forged, malformed or other-guild ID, and reports an expired one separately so the user can be told to run the command again. IDs from 1.0.5 and earlier (`rb1`) are verified and then treated as expired.
- **`context.ts`** holds the `AppContext`, the `RateLimits`, and station visibility. Pack stations are visible only while their pack is enabled, custom stations only to their own guild, and stations are sorted in pack order. `visibleStations()` keeps each server's list (at most 100 servers, least recently used dropped first) until `StationRepository.changeCount` or `PackRegistry.generation` changes, so a keystroke or a page click doesn't copy and sort the catalogue. It also holds voice-channel choice and the operator check.
- **`voice-access.ts`** validates a voice target: it exists, is a standard voice channel (not a stage), is on the allowlist, the bot has View Channel, Connect and Speak, and it is joinable. It also counts human listeners from voice states.
- **`ui/settings-view.ts`** builds the `/radio config` settings card in Discord's newer message layout (Components V2): an overview with a section and a **Change** button per group, one page per group, the four Set up steps, the reset and remove-panel confirmations, and the forms for the default station and the manual bitrate. Each screen is one container within Discord's 40-component limit, and building one reads at most the default station by ID. Its buttons and menus carry `<field>:<screen>`, so the controller (`#configComponent`, `#configForm`) saves the change and redraws the screen it came from; a card from before 1.3 (an embed) is answered with a new card instead of being edited.
- **`ui/views.ts`, `ui/format.ts`** contain the embeds and components: browse, list, the ambiguity picker, now-playing (with "Up next"), quality, sources/inspect and control rows. The control rows have two or three buttons each, so every row fits a 375-wide phone screen: **Previous** and **Next**, plus **Skip** when stations are queued (and always on the panel); **Browse** and, for a station, **Favourite** or **Unfavourite** (whichever applies, so a second click or an old message can't undo the first); **Sources** and **Inspect**; then **Refresh**, **Stop** and **Leave**. The controller handles the queue in `#queueGroup` and `#cmdSkip`, station packs in `#packsGroup` and `#packComponent` (with the views in `ui/packs-view.ts`), and builds the `/radio stats` panel in `#statsView`. The now-playing, quality, sources/inspect, browse, list and help views carry the unofficial disclaimer.
- **`notifier.ts`** sends recovery and error notices to the configured notification channel. It sends the first notice of a given kind, then counts repeats within 5 minutes and sends one summary.
- **`presence.ts`** (`PresenceUpdater`) sets the bot's own "Listening to" status from the live sessions, according to `PRESENCE_MODE`. There is one status for the whole bot, so `presenceText()` names a station only when every playing server plays that one (otherwise "radio in N servers"), never names a server's custom station, and flattens the stream title to one line of at most 128 characters. It sends only changes.
- **`voice-status.ts`** (`VoiceStatusUpdater`) sets the status of each server's bot voice channel to "📻 Station · title" on the same 20 s timer, sending only changes. It needs the optional Set Voice Channel Status permission (checked per channel) and the server's `voiceChannelStatus` setting; discord.js has no helper, so it calls `PUT /channels/{id}/voice-status` through the client's REST manager. Because only that server sees the status, a custom station can be named. When a session leaves, it stops the audio at once but keeps the voice connection open until the `onLeaving` hook has cleared the status (at most 1.5 s), because Discord refuses the change once the bot has left; a play during that wait takes over the open connection. An update works from a snapshot of the sessions and sends its requests one after another, so it could set a status for a server that has just left. To prevent that, each `clear()` bumps a per-server counter, and an update that started before the clear sets nothing more for that server. Shutdown clears every status first. A failed request is logged once and not retried until the text changes.

### `catalogue/`

- **`packs.ts`** loads and cross-validates station packs: `pack.json`, `stations.json` and an optional `sources.json`. It checks:
  - the schema, and that pack IDs are unique (`custom` is reserved);
  - that slugs are unique, and that no two stations of a pack share a name or alias;
  - declared categories, and source-to-station references;
  - that no URL is mapped to two stations;
  - that source IDs are unique across all packs.

  It also refuses a pack whose `minBotVersion` is newer than the bot. Each loaded pack records where it came from (`builtin`, `extra` or `installed`) and a hash of its files. `PackRegistry` exposes the enabled packs, pack order, categories and per-pack brand labels, and can add, replace (`put()`) and unload (`drop()`) installed packs while the bot runs; everything that asks it sees the change at once. Unloading a pack hides its stations but leaves them in the database, so favourites come back if it returns. `seedPacks()` writes every pack to the database in one transaction at start-up, and `seedPackInSlices()` writes one pack while the bot runs, in transactions of about 4 ms (at most 500 rows) with the event loop given back in between, so a pack of 2000 stations never holds up voice packets. Sources a newer version no longer lists are collected first and switched off in the same short slices. `PackRegistry.orderOf()` is a map lookup, and `generation` goes up whenever the packs change. The format and the authoring tools are described in [catalog/README.md](../catalog/README.md).
- **`pack-library.ts`** reads pack libraries: the `index.json` that lists every pack (at most 2 MiB) and the bundle file of each pack (at most 8 MiB), both fetched through `SafeHttpClient` within 20 s. `OFFICIAL_LIBRARY_URL` is fixed in the code, so Discord can only ever install from the official library. `checkBundle()` checks a download's SHA-256 against the index, that it is the pack asked for, and the pack itself with the same rules as a folder (`parsePack()`); any failure is `PACK_INVALID`. `searchLibrary()` filters the index by words, country and language.
- **`pack-store.ts`** (`PackStore`) owns the installed-packs folder (`<data>/installed-packs/<pack-id>/`) and its record, `installed.json` (version, source, SHA-256 and time of each install, and the list of packs removed on purpose). A pack is written to a hidden folder and renamed into place, so a half-written pack is never loaded. Both the bot and `scripts/packs.ts` write here.
- **`pack-manager.ts`** (`PackManager`) installs, updates and removes packs from the official library while the bot runs, reloads the installed-packs folder on `SIGHUP`, puts back missing packs at start-up, and runs the daily check. Everything heavy stays off the voice thread: a download is a network wait; checking a bundle or loading a pack folder (tens of milliseconds for a large pack) runs on a short-lived worker thread (`pack-worker.ts`, with a 30 s time limit and a heap of at most 192 MB). Copying thousands of rows back as objects would itself hold up the main thread for over 10 ms, so a bundle check sends back only what installing it needs (the files to write, as bytes moved rather than copied between threads, and the source IDs for the clash check), and a loaded pack's stations and sources come back as JSON text in chunks of 250 rows, each parsed in a turn of its own. A reload hashes each installed folder on the worker first and skips a pack whose files haven't changed. On Linux each of the bot's worker threads for background work (pack checks, list parsing, checkpoints) lowers its own CPU priority to the lowest (`lower-thread-priority.ts`); elsewhere that would lower the whole process, so it does nothing. The database is written with `seedPackInSlices()`. Installs, updates, removals, reloads and the daily check run through `SourceService.runInBackground()`, so they run one at a time with the other background work and wait while any stream is in its first 30 s; the daily check is automatic and waits for the settle period too. The library's index is reused for 10 minutes. A removed or withdrawn pack's stations stop playing at once in every server. `updates` (newer versions seen in the index) and `notices` (at most 10, such as a withdrawal) are shown by `/radio packs installed`.
- **`sync.ts`** (`CatalogueSync`) reconciles each pack that declares `sync` in its `pack.json` with that pack's official list. **`sync-adapters.ts`** holds the list parsers (`webradio-apidata` for a webradio list embedded in a station website's page, and `json-name-list`). Adapters read station names and stable IDs only. See [station-verification.md](station-verification.md#catalogue-sync). A sync is written so that it can't hold up voice packets:
  - the list page (up to 6 MB) is fetched on the main thread through `SafeHttpClient`, like all other traffic, and then handed to a short-lived worker thread (`sync-parse-worker.ts`), which decodes it, runs the adapter and sends back only the names and IDs. Parsing a 6 MB page takes 20–30 ms, too long for the main thread. A list of more than 5,000 names is refused;
  - matching the list against the catalogue (including the comparison of new names with missing ones) runs in slices of about 2 ms, giving the event loop a turn in between;
  - the changes are then written in transactions of at most 50 rows, with a turn for the event loop in between: first the stations still on the list are marked as seen today, 50 to a statement (the daily sync of an unchanged list is just these writes, one for nearly every station, which in a single statement took over 20 ms for 2000 stations), then any renames, new stations and stations missing from the list. A day's handful of changes is one transaction; each transaction is all or nothing, and the report lists only what was written, so if one fails, the next sync finishes the job;
  - only one sync runs at a time: an admin's `/radio packs sync` waits for a scheduled one that is already running.
- **`custom-provider.ts`** (`CustomStationService`) handles guild-scoped custom stations. It cleans the text fields, validates the URL with `UrlPolicy`, probes the source, and rolls back if the probe fails. It enforces the per-guild cap.
- **`search.ts`** does ranked fuzzy search. `resolveStation()` returns a match only for an exact identity (ID, slug, name or alias) or a single clearly dominant hit. Otherwise the controller shows an "ambiguous" picker. Each station's normalised names are worked out once and kept per row, the query is split once per search, and for up to 100 results it keeps a bounded, sorted top list rather than sorting every hit.

### `observability/netstats.ts` and live statistics

`/radio stats` is built by `RadioController.#statsView()` from three sources:

- `GuildSession.liveStats()`: input and output `RateMeter`s over 10 s and 60 s, HLS segment counters and last segment host, and the connected stream IP and port.
- `DiscordVoiceLink.stats()`: voice endpoint and WebSocket ping (the voice library no longer measures a UDP round trip), sampled every 5 s into a `LatencySeries` whose jitter is the mean absolute difference between neighbouring samples, and packets sent, with the late-packet count and longest gap from `PacketTiming`.
- `netstats.ts` helpers:
  - `tcpPing()` makes 5 TCP handshakes to the exact stream IP, which is re-checked against the URL policy first. It sends no HTTP request.
  - `regionHint()` turns host-name conventions (`n01-eu2.example.net` → Europe, `c-lhr05` → London) into a best-effort label, shown as "guessed from the host name".

Each enabled pack's coverage counts (every station and source of the pack) come from `SourceService.coverageByProvider()`, kept for at most 60 s, and each pack is read in a turn of the event loop of its own, so the panel's cost doesn't add up into one stretch however many packs are installed. `/radio list` adds up the same per-pack counts and counts only the server's custom stations on the spot.

### `persistence/`

`Db` wraps `node:sqlite` (`DatabaseSync`). It provides nested transactions (savepoints) and versioned SQL migrations from `migrations/`, recorded in `schema_migrations`:

- `0001_initial.sql`: the schema;
- `0002_voice_channel_status.sql`: the per-server voice channel status setting;
- `0003_probe_results_started_index.sql`: an index for the hourly clean-up of old check results;
- `0004_foreign_key_indexes.sql`: indexes on the favourites, queue and source-preference columns that point to stations and sources, so deleting a station or source doesn't read those whole tables;
- `0005_sync_reports_provider_index.sql`: an index on the sync reports by pack, so the last sync of a pack is found without reading them all (`lastSyncOutcome()` reads only its result and time).

Checksums are verified: an edited applied migration aborts start-up, and so does a database that is newer than the build. `backup()` uses `VACUUM INTO` to write a consistent copy into the `backups/` folder next to the database and rotates each kind separately: the newest 5 pre-migration backups (`pre-vN`) and the newest 10 manual ones (`backup.js`, which lowers its own process priority so that it yields to the live encoder). The rotation class is the label without its trailing digits. A backup reads through SQLite, so it includes everything, whether or not it has been checkpointed yet.

**Checkpoints.** The database runs in WAL mode: a commit appends to the write-ahead log (`radio-bot.sqlite-wal`), and a *checkpoint* later copies the log back into the database file and syncs that file to disk. By default SQLite checkpoints inside whichever commit takes the log past 1000 pages, and that commit then waits for the copy and the sync to disk (20–100 ms on slow storage) on the thread that sends voice packets. So, once the bot has started, its own connection never checkpoints (`PRAGMA wal_autocheckpoint = 0`). `WalCheckpointer` (`checkpoint.ts`) runs them instead on a worker thread with a connection of its own (`checkpoint-worker.ts`):

- every 5 min, and sooner if the log file grows past 4 MB (its size is looked at every 30 s; SQLite reuses the file after a checkpoint, so only growth beyond its largest size so far counts);
- always PASSIVE: such a checkpoint copies what it can without waiting for any lock, and takes none that the bot's connection waits for, so the bot's reads and writes carry on meanwhile. Whatever it can't copy now is copied next time;
- one at a time. The worker uses a small page cache and a heap of at most 16 MB, and on Linux runs at the lowest CPU priority.

If the worker can't start, stops, or fails three times in a row, SQLite's own automatic checkpoints are switched back on, with a warning in the log, so the log can never grow without bound. At shutdown the worker is stopped first, then the bot's connection runs a final checkpoint that empties the log, and closes the database.

The tables are listed in [rights-and-disclaimer.md](rights-and-disclaimer.md#privacy-policy-for-a-self-hosted-instance).

### `import-export/`

`config-io.ts` defines the export schema `radio-bot/guild-config` version 1: settings, pack-station favourites, prefer/pin source preferences and custom stations. Custom URLs that have a query string or credentials are redacted and flagged. A server keeps at most 1000 favourites and source choices for at most 1000 stations, and an import accepts as many. `/radio export` warns when its file is larger than an import accepts. The controller accepts a file of at most 256 KB, stored on Discord's CDN, and at most 5 imports per server in 10 minutes (`RateLimits.importGuild`). `parseImport()` validates with Zod. `previewImport()` reports what would change and warns about channels and roles that don't exist in the target server. Each server has at most one pending preview: a new `/radio import` replaces it, and the old preview's buttons then say it has expired. Nothing changes until an admin clicks **Apply import**. Exports leave out custom-station favourites and a custom default station, so `applyImport()` keeps the target server's own: its custom-station favourites follow the file's favourites in their existing order, and its custom default station stays when the file has no default. Redacted custom stations are skipped, and the rest go through the normal add path, including the probe.

### `observability/`

- **`logger.ts`**: Pino, writing JSON lines to stdout.
- **`metrics.ts`**: in-process counters and a ring buffer of 200 incidents. Repeats of the same code are coalesced within 5 minutes, and each incident is tagged with a fault domain: `upstream`, `discord`, `bot`, `operator` or `user`.
- **`health.ts`**: the heartbeat file (`health.json` next to the database) and the optional local diagnostics server. `HeartbeatWriter` writes the file asynchronously and one write at a time, atomically (a temporary file renamed over the old one), as one line of JSON. It is read by `radio-bot` (install, update, restart), by `checkHeartbeat()` in `heartbeat-check.ts` (`scripts/healthcheck.ts`, used by `radio-bot status` and bare-metal installs; kept apart from `health.ts` so it doesn't load the logger), and by the Docker image's `HEALTHCHECK`, `scripts/healthcheck.sh`, which applies the same rules without starting Node and runs every 2 minutes, unhealthy after 2 failures in a row: each check costs Docker itself about 0.1 s of CPU at normal priority, so on a one-core host it is kept rare.
- **`event-loop.ts`** (`EventLoopMonitor`): Node's event-loop delay, sampled every 10 ms and summarised per minute (typical, 99th percentile, worst), with what can explain it over the same minute: garbage collections (a `PerformanceObserver` on `gc` entries: count, full collections, longest and its kind), memory, the CPU time used and the involuntary context switches (`process.resourceUsage()`), and on Linux the host's CPU steal from `/proc/stat`, read asynchronously once a minute. Voice packets are sent every 20 ms from that loop, so `/radio stats` flags a delay of 20 ms or more. A minute with a delay or a collection of 50 ms or more is logged as a warning, which also lists that minute's late packets (`PacketTiming` keeps the last 16, with their times, in preallocated arrays); other minutes are logged at debug level. The diagnostics endpoint includes the figures. Gateway reconnects and resumes are logged at info level, so a gap can be matched to them.

## Data flow: `/radio play`

1. `RadioController` resolves the station. It accepts an ID or an exact name; an ambiguous query shows a picker.
2. It chooses the voice channel in this order: the locked preferred channel, an explicit `channel` option, the channel the bot is already in, the requester's channel, the preferred channel.
3. It authorises the `control` capability against that target, checks availability (it refuses to play a station with no known source and does not substitute another), applies the per-user and per-guild play rate limits, and defers the reply.
4. `SessionManager.play()` checks `MAX_ACTIVE_GUILD_STREAMS` and calls `GuildSession.play()`, which persists desired state `playing`.
5. The session makes sure a voice link exists. `resolveVoiceTarget()` re-checks the allowlist and the bot's permissions, then connects.
6. `SourceService.prepareForPlayback()` returns a `SelectionResult`, probing in the foreground only if no source is eligible.
7. `planEncoder()` takes the server's quality mode, the selected source's bitrate and the installation's `MAX_OPUS_BITRATE_KBPS`, and records the channel's bitrate setting for reporting. `openSourceInput()` opens the selected source through `SafeHttpClient`, which follows redirects and any playlist or HLS manifest. `AudioPipeline` starts FFmpeg and pipes the bytes in.
8. `DiscordVoiceLink.play()` hands the Ogg Opus output to the audio player.
9. When the first Opus bytes arrive (within 20 s), the state becomes `PLAYING` and the reply shows the now-playing embed and the "Why this source" explanation. After 30 s of stable playback, the source's health score goes up. Background checks of the station's other sources wait until the stream has played for 3 minutes.

## The source-validation boundary

The PRD (§12.2) requires that command handlers never construct FFmpeg commands or fetch stream URLs themselves. In the implementation:

- **Only `SafeHttpClient` talks to stream hosts.** Every URL, redirect and connection goes through `UrlPolicy`, and DNS is resolved and pinned by the client. Probes (`probe.ts`), playback (`input.ts` via the session manager), identity comparisons, the catalogue sync, pack library downloads (in the bot and in `scripts/packs.ts`) and import attachments all use it. The import attachment host is also limited to `cdn.discordapp.com` and `media.discordapp.net`.
- **Only `SourceService` probes.** It decides when a probe is needed and applies the results. Command handlers ask it for a selection, an availability state or a rescan.
- **The command layer never builds FFmpeg arguments.** The arguments are fixed lists in `encoder.ts`, `probe.ts` and `identity.ts`. User input never reaches an FFmpeg command line. The only variable values are the bitrate (an integer computed by the planner), the channel count and the sample rate.

### Why FFmpeg only ever reads stdin

Every FFmpeg and FFprobe invocation uses `-i pipe:0` with `-protocol_whitelist pipe`. It receives bytes that the bot has already fetched under the URL policy, and it is not allowed to open anything else. The reasons:

- **No SSRF through FFmpeg.** FFmpeg has its own HTTP, HLS, `concat:`, `file:`, `subfile:`, `data:` and other protocol handlers. If FFmpeg were given a URL, or a playlist or HLS manifest that points elsewhere, it would fetch those targets with its own resolver. That would bypass the private-address checks, the redirect re-validation and the DNS pinning. With the pipe-only whitelist, a hostile manifest cannot make FFmpeg open `http://169.254.169.254/` or `file:///etc/passwd`.
- **One place to enforce limits.** Timeouts, size caps, redirect limits and segment retries all live in `SafeHttpClient`, `input.ts` and `HlsReader`, where they are tested. The bot also resolves HLS itself, which lets it choose the audio rendition properly instead of following whatever FFmpeg's demuxer would pick.
- **Clean recovery.** Reconnects and failover are decided by the session, not by FFmpeg's internal reconnect options, so the state machine always knows what is playing.

## Persistence and state

- **Desired state vs runtime state.** Runtime state (the `PlaybackState`, the pipeline and the link) lives in memory only. Desired state lives in `guild_playback_state` and survives restarts. An explicit stop, leave or kick is persisted and suppresses autostart.
- **Boot policy** (`bootDecision()`):
  - If desired state was `playing` or `paused_empty` and the server enabled *Resume after restart*, the bot resumes in the saved channel.
  - Otherwise, if *Autostart* is on, a default station and preferred channel are set, and no explicit stop, leave or kick is on record, it starts the default.
  - Otherwise it stays idle. If playback was desired but resume is off, the bot records `RESUME_DISABLED`, which `/radio status` explains.
  - Resume and autostart skip retired stations and stations the server can no longer see (for example a pack switched off with `DISABLED_PACKS`), using the same visibility rule as the commands.
  - Leaving an empty channel after `/radio stop` keeps the desired state *stopped*, so autostart stays suppressed.
- **Station facts** (codec, bitrates, identity evidence, health, cooldown) are shared by all guilds. **Preferences** (pin and prefer), favourites and settings are per guild.

## Concurrency and resource bounds

- At most one voice connection and one encoder FFmpeg process per guild, and at most `MAX_ACTIVE_GUILD_STREAMS` guilds streaming. The limit is enforced on every path that starts a stream, including resume from pause, retries and voice reconnects.
- At most `MAX_CONCURRENT_PROBES` probes at once, and one per host. Each probe runs one `ffprobe` and one `ffmpeg` over a sample of at most 2 MiB. An identity comparison decodes two samples of 40 s each, at most 4 MiB each, within 90 s. HLS is opened 1 segment from the live edge for comparisons.
- The HLS reader's internal buffer is bounded (512 KiB high-water mark plus one segment of at most 16 MiB). Back-pressure stops fetching when FFmpeg is not reading.
- Pack downloads are capped (2 MiB for a library index, 8 MiB for a bundle), checked on a worker thread with a heap of at most 192 MB, and written in transactions of about 4 ms. At most 10 pack changes an hour are accepted from Discord (`RateLimits.packGlobal`), and pack jobs run one at a time with the other background work.
- The rate-limiter maps and incident ring are bounded or swept. An open browse list expires 15 minutes after it was last used, and at most 500 are kept (the oldest go first); a list with a search keeps its results (at most 500 IDs) so a page click doesn't search again. There is at most one import preview per server, and it expires after 10 minutes. The prepared-statement cache holds at most 500 statements.
